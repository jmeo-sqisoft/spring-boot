# 백엔드 테스트 작성·검증 가이드

테스트 파일을 생성하거나 수정할 때 적용하는 공통 규칙입니다.
변경한 기능에 필요한 검증 범위를 선택하며, 아직 구현하지 않은 인증·집계 등의 기능까지 추가하지 않습니다.

## 1. 파일 구성과 컴파일 오류 방지

- 테스트는 `src/test/java` 아래에 두고 운영 코드와 같은 패키지 경로를 사용한다. 기본 파일명은 `대상클래스명Test.java`로 하며, 여러 클래스를 함께 검증하면 `SampleConvertersTest`처럼 검증 대상을 드러내는 이름을 사용한다. 최상위 타입 이름과 파일명을 일치시킨다.
- 저장소에 설정된 Java 21과 JUnit Platform에 맞춰 작성한다. 기존 테스트의 JUnit Jupiter·Mockito·AssertJ 사용 방식을 확인하고 필요한 범위에서 재사용한다.
- 대상 클래스의 현재 생성자, 메서드 시그니처, 반환 타입, 요청·응답·조회 모델을 실제 코드와 대조한다. 이름이 비슷한 다른 타입이나 이전 시그니처를 가정해 테스트를 만들지 않는다.
- 테스트용 의존성과 애너테이션 처리기 설정을 확인한다. 운영 코드의 `annotationProcessor` 설정이 테스트에도 자동 적용된다고 가정하지 않는다.
- 공용 인터페이스·생성자 변경 시 구현체와 테스트 호출부를 함께 확인한다. 일부 파일만 반영되어 컴파일이 깨지는 상태를 남기지 않는다.
- 파일은 UTF-8로 저장하고 파일 끝에 줄바꿈을 둔다. 탭 대신 공백 4칸으로 들여쓰고, 클래스 선언 직후에 빈 줄을 두지 않는다. 불필요하거나 중복된 import를 제거하고, Java 가이드의 예외 대상 외에는 한 줄을 최대 100자로 작성한다.
- 신규·수정 설명 주석은 한국어로 작성하며 식별자와 기술 용어는 유지한다. 기존 테스트 제목을 범위 밖까지 일괄 번역하지 않는다.

## 2. 검증 시나리오와 기대값

- 테스트 이름, 입력, 실행 조건, 검증 내용이 같은 동작을 표현하도록 작성한다.
- 변경한 동작에 대해 정상·실패·경계 조건을 구분한다. 해당 입력 계약의 null·빈 값·누락·중복·허용값·기간 경계를 함께 확인한다.
- 기대값은 승인된 업무 계약과 독립적인 계산 근거에서 도출한다. 현재 구현이 반환한 값을 그대로 정답으로 삼지 않는다.
- 구현을 변경했다는 이유만으로 기존 거절 테스트를 성공 테스트로 바꾸거나, 실패하는 assertion을 삭제·약화하지 않는다.
- 단순히 예외가 없거나 결과가 null이 아니라는 사실만 확인하지 않는다. 변경된 값·상태·오류·반환 구조·관련 호출 여부를 검증한다.
- enum이나 공통 타입의 허용값을 늘릴 때는 필드별 허용값과 거절 조건을 검증한다. 조건에 따라 호출 API·조회 식별자가 달라지면 올바른 분기와 불필요한 호출의 부재를 확인한다.
- 선택 의존성이나 환경변수를 추가하면 미설정·일부 설정·정상 설정을 구분한다. 데이터 부재나 오류를 정상 값으로 바꾸어 테스트를 통과시키지 않는다.
- 공용 코드 변경 시 기존 소비자의 기본값·수치·오류·상태 계약을 보호한다. 특정 업무의 새 정책을 다른 소비자에도 적용하는 회귀를 확인한다.

## 3. 테스트 데이터와 mock 작성

- fixture와 mock은 실제 조회 조건 및 SQL이 반환할 수 있는 데이터로 구성한다. 테스트를 통과시키기 위한 불가능한 행 조합을 만들지 않는다.
- 해당 기능에서 의미가 다른 정상 값·0·빈 조회·null·잘못된 값을 구분한다. 계약상 허용되지 않는 데이터는 실패 시나리오로 명시한다.
- 오류나 자료 부재를 기본값·빈 목록·0 반환으로 숨기는 mock을 만들지 않는다.
- 시간·조회 기간에 의존하는 테스트는 고정 `Clock`이나 명시적인 기준 시각을 사용하고, 조회 범위와 날짜 fixture를 일치시킨다. 시스템 시각·기본 시간대·실행 순서에 따라 결과가 바뀌지 않게 한다.
- 테스트별로 독립적인 데이터를 사용한다. 변경 가능한 static 값·공유 컬렉션을 수정한 경우 다른 테스트에 상태가 남지 않게 한다. 임의의 대기 시간으로 비동기 완료를 추정하지 않는다.
- 목록의 특정 index나 의미가 드러나지 않는 값에 의존하는 검증은 실제 정렬·식별 계약과 대조한다. 테스트 이름과 fixture의 의미가 다르면 수정한다.
- 단위 테스트의 대역과 실제 외부 시스템을 구분한다. 모든 테스트에 `@SpringBootTest`를 사용하거나, 단위 테스트의 성공을 위해 실제 DB·서버 연결을 추가하지 않는다.

## 4. Assertion과 예외 검증

- 변경된 응답 필드를 검증에서 빼거나 값을 확인하지 않고 건너뛰지 않는다. 값의 존재·부재·null·예상 결과를 업무 계약에 맞게 명시적으로 검증한다.
- 예외 검증 람다에는 예외를 검증할 호출 하나만 둔다. 객체·요청·컬렉션 생성, 날짜 계산과 getter 호출은 람다 밖 준비 단계에서 수행한다. 생성자 자체가 검증 대상이면 해당 생성자만 람다에 남긴다.
- 여러 호출을 helper 안에 숨겨 예외 발생 위치가 모호해지는 방식으로 우회하지 않는다.
- 비어 있으면 안 되는 컬렉션에 `allSatisfy`, `allMatch`, `doesNotContain` 등을 사용하면 먼저 `isNotEmpty`, 기대 크기 또는 정확한 원소를 검증한다. 빈 목록도 통과하는 assertion으로 데이터 누락을 놓치지 않는다.
- 동일한 대상 값의 연속 assertion은 하나의 AssertJ chain으로 연결한다. 서로 다른 대상이나 중간에 상태가 달라지는 검증을 억지로 합치지 않는다.
- 검증 항목·기대값·순서를 유지한다. 빈 줄, helper, 경고 억제로 품질 지적을 숨기지 않는다.

## 5. Controller·요청 검증·인증·인가 테스트

- 요청 바인딩·Bean Validation·예외 응답을 바꾸면 실제 HTTP 검증 경계를 통과하는 테스트로 확인한다. 직접 객체를 생성하고 Java 메서드를 호출한 결과만으로 HTTP 계약을 검증했다고 판단하지 않는다.
- 잘못된 요청은 API 계약에 맞는 HTTP 상태·오류 코드·메시지·응답 구조를 검증한다. 필드 오류를 제공하는 API는 필드 오류도 확인한다. 입력 검증 단계에서 거절된 요청은 Service 또는 Mapper가 호출되지 않는지 확인한다.
- `@NotNull`·`@Valid`만 붙어 있으면 직접 Java 생성·호출에서도 검증이 자동 실행된다고 가정하지 않는다. 검증을 record 생성자로 옮긴 경우 기존 HTTP 오류가 500으로 바뀌지 않는지 확인한다.
- Bean Validation을 사용하는 경우 검증 의존성과 실제 Validator를 확인한다. 메시지는 기존 MessageSource 키를 재사용하며, 다국어 응답은 `Accept-Language`와 메시지 리소스로 지원 언어·기본 언어 처리를 검증한다.
- 인증·인가 기능을 추가하거나 수정하는 경우 정상 요청, 무인증, 잘못된 인증, 권한 없음, 범위 밖 데이터를 구분해 검증한다. 인가 단계에서 거절된 요청의 Mapper 미호출도 확인한다.
- 호출자의 인증 여부, API 사용 권한, 조회 가능한 데이터 범위를 별도로 검증한다. 헤더 존재나 JWT 파싱 성공만으로 인증·인가가 완료됐다고 판단하지 않는다.
- 인증을 Gateway로 이관한 경우 직접 BE 접근과 위조된 호출자 헤더의 차단을 별도 검증 대상으로 둔다. 로컬 대역 테스트 통과를 외부 배포 경계 검증으로 표현하지 않는다.

## 6. Service·트랜잭션 테스트

- 조회·계산·응답 변환의 변경 결과와 관련 Mapper 호출을 검증한다. 조회 우선순위·기본값·null 조건 처리가 바뀌면 전달 인자와 호출 여부도 확인한다. 단순 리팩터링으로 바뀔 수 있는 내부 호출 순서까지 불필요하게 고정하지 않는다.
- 트랜잭션 설정을 변경하면 Spring proxy 또는 `TransactionTemplate`을 통과하는 테스트로 readOnly·격리 수준·전파 설정과 정상 완료·예외 동작을 확인한다.
- 어노테이션 존재 검사, 직접 `new`로 만든 객체 호출, self-invocation만으로 트랜잭션 적용을 보증하지 않는다. private/final 메서드 및 외부 `REQUIRED` 트랜잭션 참여 경로도 구분한다.
- 통합 테스트에서는 검증 대상인 트랜잭션 경로를 대역이나 우회 경로로 교체하지 않는다. 실제 검증 범위에 따라 정상 완료의 commit, 예외 발생 시 rollback 여부와 데이터 변경 결과를 확인한다.
- 대역 transaction manager를 통과한 검증은 실제 DB 스냅샷 검증과 구분한다.
- Bean 등록 문제를 검증할 때는 실제 프로필·스캔·등록 결과를 확인한다. 실제 후보가 하나인 상황에서 IDE 경고만 없애기 위해 `@Primary`·`@Qualifier`나 주입 구성을 바꾸지 않는다.

## 7. Mapper·SQL·TypeHandler 테스트

- 수정한 Java Mapper 메서드와 XML statement id, 매개변수, 반환 모델 및 `resultType`·`resultMap`의 일치를 확인한다. 중첩 collection·constructor 매핑을 변경하면 결과 모델 변환도 검증한다.
- MyBatis XML을 로드하고 `<include>`, `<if>`, `<choose>`를 적용한 각 지원 분기의 `BoundSql`과 바인딩을 확인한다. 정규식으로 XML 일부만 검사한 결과를 실제 렌더링 검증으로 대신하지 않는다.
- XML·SQL 포맷은 MyBatis 가이드를 따른다. 값은 `#{...}`로 바인딩하고 `${...}`는 사용하지 않는다. 동적 SQL을 변경하면 실제 렌더링 결과와 바인딩 순서를 확인한다.
- 필수 목록은 null·빈 목록·null 원소의 거절을 검증한다. 선택 목록은 null·빈 목록이 필터 생략인지 실제 빈 배열 조건인지 구분해 검증한다.
- PostgreSQL 배열 TypeHandler를 추가하거나 수정하면 원소 타입에 맞는 `createArrayOf`·`setArray` 사용과 배열 자원 해제를 검증한다. 문자열·정수·bigint·UUID 배열을 같은 타입으로 가정하지 않는다.
- 조회 컬럼·중복 제거·조인 변경 시 반환 필드, 정렬, null 처리, 조회 범위와 중복 행의 영향을 확인한다. mock 결과만으로 실제 조인이나 집계 SQL의 정확성을 보증하지 않는다.
- SQL 렌더링 테스트와 실제 DB에서의 쿼리 실행 검증을 구분한다. 실제 조회가 0행이면 비어 있지 않은 데이터에서의 검증까지 완료한 것으로 보고하지 않는다.
- 실제 DB를 사용하는 테스트는 전용 테스트 환경과 데이터 범위를 명시하고 운영 DB를 사용하지 않는다. 더미 DB 환경변수는 DB 미사용 테스트용이며 실제 JDBC 접근의 성공을 보장하지 않는다. 소스·로그·보고서에 접속 비밀번호나 토큰을 기록하지 않는다.

## 8. 계산·기간·집계 회귀 테스트

- 계산·기간·집계 기능을 추가하거나 수정할 때 적용한다. 해당 기능이 없는 변경에서는 별도 집계 테스트를 만들지 않는다.
- 정상 값의 합계와 상태를 함께 확인한다. 여러 응답이 같은 지표를 제공하면 서로 일치하는지 대조한다.
- 정상 0, 원천 오류, 산출 불가, 비교 기간 부재를 구분한다. 빈 구간을 채우는 기본값이 오류 상태를 덮지 않도록 검증한다.
- 비교 기간의 입력을 서로 다르게 구성하고, 현재 값·이전 값·차이·증가율을 독립 기대값으로 검증한다.
- 기간 변경은 고정 기준 시각과 명시적인 시간대를 사용한다. 시작·종료 경계의 포함 여부, 기간을 걸치는 데이터, 빈 기간을 구분한다.
- 평균·비율·예측 계산은 분모, 정수 나눗셈, 연산 순서, 정밀도와 반올림 시점을 독립적으로 확인한다. 보관된 원천 입력을 덮어쓰거나 현재 출력에 맞춰 기대값을 변경하지 않는다.
- 기간·반올림·0 입력·가용성 정책을 바꾸면 관련 조건부 테스트의 기대값과 fixture도 확인한다. 핵심 계산 경계는 외부 DB 없이 실행되는 단위 테스트로도 보호한다.
- 조건부 테스트는 실행·실패·스킵을 구분한다. 환경 요건이 충족된 검사만 실제 활성화하며, 스킵된 검사를 성공 건수에 포함하지 않는다.
- 계산 정책의 의미가 바뀌면 영향 범위의 값·상태·기간·응답 메타데이터를 함께 검증한다. 별도 정책 버전 계약이 있으면 해당 계약도 확인한다.

## 9. 테스트 코드의 Java 품질 기준

다음은 코드 리뷰 기준이다. Sonar 규칙 ID는 참고용이며 실제 활성 여부·임계치·테스트 코드 적용 범위는
연결된 서버의 Quality Profile과 분석 설정으로 확인한다.

| 항목 | 작성 기준 |
|---|---|
| boolean 명명 | 의미가 드러나는 camelCase를 사용하고 `is`·`has`·`should` 접두사는 의미에 맞을 때 사용한다. 명명 변경으로 조건식·기대값·동작·API/JSON 계약을 바꾸지 않는다. |
| 인지 복잡도 (`java:S3776`) | 분기·반복문 추가 시 메서드 전체의 복잡도를 확인한다. 목적이 분명한 준비·변환은 작은 private 함수로 분리하되 조건·호출 순서·원본 상태를 유지한다. 임계치 상향이나 불필요한 계층으로 우회하지 않는다. |
| 정수 나눗셈 (`java:S2184`) | 정수 몫이 계약이면 먼저 정수 변수로 계산하고, 소수 몫이 필요하면 나누기 전에 실수로 변환한다. 계산 후 cast나 일률적인 실수 변환으로 절삭·반올림 결과를 바꾸지 않는다. |
| null 흐름 (`java:S2259`) | nullable 객체를 boolean flag만으로 간접 보호하지 않는다. null 검사 분기 안에서 필요한 객체를 생성·사용하고 fallback으로 원천 오류를 숨기지 않는다. |
| 항상 같은 조건·Validation (`java:S2583`) | 필수값 계약과 항상 false인 검사를 대조한다. 중복 검사를 정리할 때도 실제 HTTP 검증 경계와 기존 거절 계약을 보호한다. |
| 메서드 재정의 (`java:S1161`) | 테스트 대역을 포함해 인터페이스 구현 및 상위 메서드 재정의에 `@Override`를 붙인다. |
| 예외 람다 (`java:S5778`) | 예외를 검증할 호출 하나만 람다에 남긴다. 준비 호출을 밖으로 빼고, 복수 호출을 helper에 숨기지 않는다. |
| 과도한 인자 (`java:S107`) | 인자가 많아 의미 파악이 어려우면 책임과 의미가 같은 조건 묶음을 검토한다. 임계치만 맞추려고 무관한 값을 묶거나 공개 계약을 바꾸지 않는다. |
| 중첩 삼항식 (`java:S3358`) | 조기 반환이나 명시적 if로 분리한다. 분리하면서 지연 실행·호출 조건을 바꾸지 않는다. |
| 문자열 중복 (`java:S1192`) | 같은 의미로 반복하는 문자열은 기존 상수를 재사용하거나 의미 있는 `private static final` 상수로 관리한다. 우연히 같은 값인 다른 의미의 문자열까지 합치지 않는다. |
| 반복문 제어 (`java:S127`) | for 제어 변수를 본문에서 재대입하지 않는다. 가변 간격 순회는 while 등으로 진행·종료 조건을 명확히 한다. |
| 메서드 참조 (`java:S1612`) | `map`·AssertJ `extracting`의 단순 getter·전달 람다는 가독성이 좋아지는 메서드 참조로 표현한다. 계산·조건 람다까지 기계적으로 바꾸지 않는다. |
| 빈 목록의 허위 통과 (`java:S5841`) | 비어 있으면 안 되는 컬렉션은 전체 원소·부정 조건을 확인하기 전에 비어 있지 않음, 기대 크기 또는 정확한 원소를 검증한다. |
| 동일 대상 assertion (`java:S5853`) | 동일 대상의 연속 검증을 하나의 AssertJ chain으로 연결한다. 검증 항목·기대값·순서를 유지하고 서로 다른 대상이나 상태 전후 검증은 억지로 합치지 않는다. |

경고 억제, `NOSONAR`, 규칙 비활성화, 복잡도 임계치 상향, 분석 대상 제외로 문제를 통과시키지 않는다. 테스트 diff에도 위 기준을 적용한다.

## 10. 생성 후 실행·검증 기준

- 새로 추가하거나 변경한 테스트가 실제로 컴파일되고 실행됐는지 확인한다. 테스트 수, 실패·오류·스킵과 선택된 클래스를 확인하며 과거 보고서를 이번 실행 결과로 사용하지 않는다.
- 테스트만 실행하면 Checkstyle까지 완료된다고 가정하지 않는다. 현재 `checkstyleTest`는 비활성화되어 있으며, `checkstyleMain`은 운영 Java와 `src/main/resources`의 XML만 검사한다. 테스트 작성 기준은 별도로 검토한다.
- Checkstyle의 실제 활성 규칙과 테스트 소스에 적용되는 예외를 확인한다. Checkstyle 통과만으로 boolean 명명·assertion·Sonar 기준까지 검증됐다고 판단하지 않는다.
- 작은 국소 변경은 관련 테스트·정적 검사를 수행하고, 사용 중인 IDE에 SonarQube for IDE가 연결되어 있으면 해당 파일 분석도 확인한다. 영향이 큰 변경은 BE 프로젝트에서 변경 파일 분석을, 공용 설정 등 프로젝트 전반에 파급되면 전체 분석을 확인한다.
- 테스트·Checkstyle·일반 IDE inspection·IDE Sonar·서버 Quality Gate·원격 리뷰는 각각의 결과를 구분한다. 일반 검사 0건이나 workflow 성공만으로 Sonar 또는 서버 Gate 통과를 선언하지 않는다.
- 서버 분석이나 외부 환경 검증을 실행하지 못하면 그 항목과 범위를 명시한다. 실행하지 않은 검증, 스킵된 테스트, 진단용 테스트의 통과를 제품 수정 완료로 바꾸어 보고하지 않는다.
